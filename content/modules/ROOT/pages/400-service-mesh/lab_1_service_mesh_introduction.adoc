== Introduction

As applications evolve into collections of decentralized microservices, monitoring and managing network communication and security among those services becomes more challenging.

Red Hat OpenShift Service Mesh *3* is based on the upstream Istio project and is managed by the Red Hat OpenShift Service Mesh Operator (Sail Operator API).
It provides a uniform way to connect, manage, and observe microservices-based applications without requiring application code changes.

Official docs: https://docs.redhat.com/en/documentation/red_hat_openshift_service_mesh/3.3/html/installing/ossm-installing-service-mesh[Installing OpenShift Service Mesh 3].

== Why Red Hat OpenShift Service Mesh?

Applications are changing from monoliths into collections of small, independent, loosely coupled services.
Managing communication, security, and observability across those services is difficult without a dedicated data plane.

With OpenShift Service Mesh 3 you get:

* A production-supported Istio control plane on OpenShift (`istiod`)
* Automatic sidecar injection for labeled namespaces
* Traffic management with VirtualServices, DestinationRules, and an injected ingress gateway exposed via OpenShift Routes
* Observability through Kiali (plus OpenShift user-workload monitoring for Istio metrics)

== Service Mesh 3 architecture

OpenShift Service Mesh 3 is assembled from a small set of custom resources and add-ons you install explicitly:

* *Operator* — Red Hat OpenShift Service Mesh 3 (`servicemeshoperator3`) provides the Sail Operator APIs and Istio CRDs.
* *Control plane* — an `Istio` resource (`sailoperator.io`) deploys `istiod`, typically in `istio-system`.
* *CNI* — an `IstioCNI` resource runs the mesh CNI DaemonSet in a separate project (typically `istio-cni`).
* *Namespace membership* — discovery selectors on the `Istio` CR plus labels such as `istio-discovery=enabled` and `istio-injection=enabled` enroll application projects.
* *Gateways* — not created by the Operator; you deploy gateway injection (or Gateway API) yourself and expose traffic with an OpenShift Route when needed.
* *Kiali / tracing* — install and configure separately (Kiali Operator; Tempo / OpenTelemetry if you want distributed tracing).

== Benefits

=== Ready for production

OpenShift Service Mesh is validated and supported on Red Hat OpenShift, including ROSA.

=== Security-focused

Transparent mTLS options and fine-grained authorization policies support zero-trust networking patterns.

=== Based on open source

Service Mesh 3 tracks upstream Istio closely while remaining a Red Hat supported product.

== Use cases

* Connectivity: traffic shifting, canary / blue-green, circuit breaking, VirtualServices
* Security: encryption in transit, authentication, authorization
* Control: policy enforcement and configuration lifecycle
* Observability: Layer 7 metrics, graphs, and tracing (with optional Kiali / Tempo stack)

== What you will do in this module

. Install the OpenShift Service Mesh 3 Operator (and Kiali Operator for the observe lab).
. Deploy the Istio control plane (`Istio`) and CNI plugin (`IstioCNI`).

. Shift traffic with a weighted VirtualService, wire OpenShift user-workload monitoring for Istio metrics, and observe the mesh in Kiali.
