== Introduction

Red Hat OpenShift Service on AWS (ROSA) provides fully-managed cluster upgrades. The ROSA Site Reliability Engineering (SRE) Team monitors and manages ROSA upgrades. Customers get status emails from the SRE team before, during, and after the upgrade. Updates can be scheduled from OpenShift Cluster Manager (OCM) or from the ROSA CLI.

On *ROSA with hosted control planes (ROSA HCP)*, upgrades are split:

* *Hosted control plane* — upgraded with `rosa upgrade cluster`
* *Machine pools* (worker nodes) — upgraded separately with `rosa upgrade machinepool`

Control plane and machine pools upgrade independently. Each machine pool must remain within *two minor (Y-stream) versions* of the hosted control plane.

There are two ways to schedule an upgrade — OpenShift Cluster Manager or the `rosa` CLI. In this lab environment you do not have access to OpenShift Cluster Manager, so you will use the `rosa` CLI.

== Upgrade using the `rosa` command line interface

. Remind yourself of the version of your cluster:
+
[source,sh,role=execute]
----
oc version
----
+
.Sample Output
[source,text,options=nowrap,subs="attributes"]
----
Client Version: {rosa_version}
Kustomize Version: v5.0.1
Server Version: {rosa_version}
Kubernetes Version: v1.27.6+f67aeb3
----

. List available versions for a hosted control plane upgrade (depending on when you run this command there may not be any upgrades available):
+
[source,sh,role=execute]
----
rosa list upgrades -c rosa-$GUID
----
+
.Sample Output
[source,text,options=nowrap,subs="attributes"]
----
VERSION  NOTES
{rosa_version_next}   recommended
----
+
[TIP]
====
`rosa list upgrade` is an alias of `rosa list upgrades`. To list versions available for a machine pool, add `--machinepool workers`.
====

. If no upgrade versions are listed, you can still read the rest of this module to learn the HCP upgrade flow, then skip the schedule/cancel steps.
+
Otherwise set a variable for the cluster version you want to upgrade to. For the example above this would be:
+
[source,sh,role=execute,subs="attributes"]
----
export CLUSTER_VERSION="{rosa_version_next}"
----

. Optional but recommended: run a dry-run to surface any upgrade gates before scheduling:
+
[source,sh,role=execute]
----
rosa upgrade cluster -c rosa-$GUID --version $CLUSTER_VERSION --dry-run
----

. You probably do not want to upgrade the cluster immediately in this lab. Schedule an update 24 hours from now instead.
+
`--schedule-date` / `--schedule-time` are interpreted as *UTC*. On the lab bastion (GNU `date`):
+
[source,sh,role=execute]
----
export UPGRADE_DATE=$(date -u -d "+24 hours" '+%Y-%m-%d')
export UPGRADE_TIME=$(date -u '+%H:%M')

echo Date: $UPGRADE_DATE, Time: $UPGRADE_TIME UTC
----
+
.Sample Output
[source,text,options=nowrap]
----
Date: 2023-11-10, Time: 09:11 UTC
----

. Schedule the *hosted control plane* upgrade to the selected version.
+
[IMPORTANT]
====
Do *not* pass `--control-plane`. That flag is deprecated on current `rosa` CLI releases and can be omitted; `rosa upgrade cluster` already targets the hosted control plane on ROSA HCP.
====
+
[source,sh,role=execute]
----
rosa upgrade cluster \
  -c rosa-$GUID \
  --version $CLUSTER_VERSION \
  --mode auto \
  --schedule-date $UPGRADE_DATE \
  --schedule-time $UPGRADE_TIME \
  --yes
----
+
.Sample Output
[source,text,options=nowrap,subs="attributes"]
----
I: Ensuring account and operator role policies for cluster '27d52mumr4suemsl365a7c107400jbct' are compatible with upgrade.
I: Account roles with the prefix 'ManagedOpenShift' have attached managed policies.
I: Cluster 'rosa-{guid}' operator roles have attached managed policies. An upgrade isn't needed
I: Account and operator roles for cluster 'rosa-{guid}' are compatible with upgrade
I: Upgrade successfully scheduled for cluster 'rosa-{guid}'
----

. Verify the scheduled upgrade:
+
[source,sh,role=execute]
----
rosa describe upgrade -c rosa-$GUID
----

. On ROSA HCP, worker nodes are *not* upgraded by `rosa upgrade cluster`. After the control plane supports the target version, schedule a machine pool upgrade (default pool name on single-AZ HCP is `workers`):
+
[source,sh,role=execute]
----
rosa list upgrades -c rosa-$GUID --machinepool workers
----
+
[source,sh,role=execute]
----
rosa upgrade machinepool workers \
  -c rosa-$GUID \
  --version $CLUSTER_VERSION \
  --schedule-date $UPGRADE_DATE \
  --schedule-time $UPGRADE_TIME \
  --yes
----
+
[NOTE]
====
In this short lab you may skip actually scheduling the machine pool upgrade if no pool upgrade versions are listed, or if you already scheduled the control plane and want to cancel everything before the environment expires.
====

. Cancel the scheduled upgrade(s) so the lab environment is not left with a pending update (the environment will be deleted before the +24h window anyway):
+
[source,sh,role=execute]
----
rosa delete upgrade -c rosa-$GUID --yes
----
+
To cancel a machine pool schedule (if you created one):
+
[source,sh,role=execute]
----
rosa delete upgrade -c rosa-$GUID --machinepool workers --yes
----

*Congratulations!*

You've successfully practiced scheduling (and canceling) a ROSA HCP control plane upgrade with the `rosa` CLI, and learned that machine pools upgrade separately.

== Summary

Here you learned:

* ROSA upgrades are monitored and managed by the ROSA SRE team
* On ROSA HCP, upgrade the hosted control plane with `rosa upgrade cluster` (no `--control-plane` flag)
* Upgrade worker capacity separately with `rosa upgrade machinepool`
* Schedule, describe, and delete upgrades from the `rosa` CLI; schedule times are UTC

== Upgrade using the OpenShift Cluster Manager

[WARNING]
====
This section is for your information only. You do *not* have access to the OpenShift Cluster Manager. Feel free to read through these instructions to understand how to do it via the console — or skip to the next section. Console labels and screenshots may change over time; prefer the ROSA CLI steps above for this workshop.
====

. Log back into the OpenShift Cluster Manager by https://console.redhat.com/openshift[clicking here,window=_blank].
. In the _Clusters_ section, locate your cluster and click on it.
+
image::ocm-cluster-list.png[OCM - Cluster List]

. Next, click on the _Settings_ tab.
+
image::ocm-cluster-detail-overview-settings.png[OCM - Cluster Detail Overview Settings]

. Next, select the _Update_ button in the _Update status_ sidebar.
+
image::ocm-update-status.png[OCM - Update Status]

. Now, you're presented with a number of versions.
For this exercise, we'll select the recommended version, and then hit _Next_.
+
image::ocm-update-version-select.png[OCM - Update Version Select]

. Next, choose to _Schedule a different time_ and change the date box to 1 day from now, then select _Next_.
+
image::ocm-update-schedule-select.png[OCM - Update Schedule Select]

. Finally, select the _Confirm Update_ button and then the _Close_ button.
+
image::ocm-update-confirm.png[OCM - Update Confirm]
+
image::ocm-update-close.png[OCM - Update Close]
